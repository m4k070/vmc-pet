# M5Stack を第二の体として実装する計画

> `docs/DESIGN.md` の「将来の拡張(体を付け替える実験の足場として)」で見据えていた
> 「体を差し替える実験」の第一弾。PC上のウィンドウ(既存のvmc-pet)とは別に、
> M5Stack 単体で完結する**もう一つの体**を作る。

## 位置づけ: PC版の表示器ではなく、独立した第二の体

M5Stack-chan の既存の顔アバターを PC 側 Lenia の気分状態(`energy` など)で
ネットワーク越しに操る案(以下「案B」)も検討したが、採らない。それは
「場の状態→表情への翻訳レイヤー」を新たに作ることになり、`docs/DESIGN.md`
コンセプト節が最初から避けたかった「別途見た目を作るレイヤー」を持ち込んでしまう。

採用するのは、**M5Stack が Lenia の場を自前で計算し、自前の画面に描く、独立した体**
という案(以下「案A」)。PC版と同じ Lenia の規則を使うが、両者は互いに通信しない
別々のインスタンスになる。「体の状態がそのまま表現になる」というコンセプトの核を
壊さずに済む。

## 対象ハードウェア: M5Stack CoreS3 (確定)

| 項目 | 値 |
|---|---|
| モデル | M5Stack CoreS3 |
| チップ | ESP32-S3(Xtensa) |
| 画面 | 320x240 (ILI9342C系)。現行の 32x32 グリッドを 1セル=7px 相当で描ける
  (PC版の 384x384 ウィンドウよりむしろ余裕がある) |
| 入力 | 静電容量タッチ + 電源ボタン(物理 A/B/C ボタンは無い) |

このサンドボックス環境に実機を USB 接続して確認した。ESP32-S3 内蔵の
USB-JTAG/シリアルデバッグユニット(VID:PID `303a:1001`、Espressif)として
認識され、`/dev/ttyACM1` にシリアルポートが生える(`dialout` グループに
入っていれば追加設定なしでアクセスできる)。

## ツールチェーンの現実(このサンドボックスで検証済み)

`nix eval` で確認した限り、以下は nixpkgs にある。

| パッケージ | 役割 |
|---|---|
| `espflash` (4.4.0) | ビルド済みバイナリを実機に書き込む・シリアル監視する |
| `espup` (0.17.1) | Xtensa 対応 Rust ツールチェーンをインストールする公式ツール |
| `rustup` (1.29.0) | espup が前提とする Rust ツールチェーン管理。素の nixpkgs の
  rustc/cargo は espup が認識しないため別途要る |
| `esp-generate` (1.3.0) | esp-hal ベースのプロジェクト雛形を生成する |
| `ldproxy` (0.31.4) | esp-idf(std)ビルド時のリンカプロキシ |

一方で **`esp-idf` 本体は nixpkgs に無い**。ESP32-S3 は Xtensa アーキテクチャ
であり、upstream の rustc は Xtensa をターゲットにできないため、`espup` が取得する
Espressif フォークの rustc が必須になる。この取得は Nix のビルドサンドボックス
の外側で行う一回限りのインストール作業(`espup install`)で、PC版の `flake.nix`
のような「`nix develop` するだけで完全に再現される」体験にはならない。

**実際にこのサンドボックスで `espup install --targets esp32s3` を実行し、
ESP32-S3 向け Xtensa Rust ツールチェーン(`xtensa-esp32s3-none-elf` を含む)の
インストールを完了した。** `dl.espressif.com` / `github.com` への到達性があれば
動く。所要時間・ダウンロード量はネットワーク次第(このサンドボックスでは
数分程度)。

書き込み(`espflash flash`)・実機での動作確認は、実機がこのマシンに接続されて
いる間はここでも試せるが、恒常的な開発は素直にユーザー自身のマシンで行うのが
現実的(このサンドボックスは会話が終われば消える)。

## std (esp-idf-hal) か no_std (esp-hal) か

| | esp-idf-hal (std) | esp-hal (no_std, 推奨) |
|---|---|---|
| `body/` の再利用 | ほぼそのまま(f32 の `.sqrt()` 等が使える) | 数学関数だけ差し替えが要る(下記) |
| ビルドの重さ | ESP-IDF(C SDK)を追加取得。ネットワーク依存 | 純粋 Rust のみ。取得は Xtensa rustc だけ |
| 開発の勢い | 安定しているが esp-rs の主軸は no_std 側に移りつつある | 活発に開発が進んでいる |
| WiFi等が要るなら | 素直 | 後から `esp-wifi` crate を足せる |

今回は「M5Stack自身のCPU負荷」のような外部入力は使わない(後述)ため WiFi は
不要で、esp-idf という重い C SDK を抱える理由が無い。**no_std (`esp-hal`) を推奨**する。

### no_std にすると何が壊れるか(実測済み)

`#![no_std]` の下で `f32` のどのメソッドが使えるかを、実際にコンパイルして確認した。

```rust
// core だけで使える(変更不要)
x.abs()  x.clamp(a, b)  x.max(y)  x.min(y)
i32::rem_euclid  // 整数版はOK

// std が要る(no_std ではコンパイルエラー)
x.sqrt()  x.cos()  x.exp()  x.powi(n)  x.floor()  x.ceil()  x.round()
```

`body/` 内でこれらが実際に使われている箇所を数えると、影響は小さい
(テストコードのみで使う `.hypot()` `.round()` は本番ビルドには含まれない)。

| メソッド | 使用箇所 |
|---|---|
| `.sqrt()` | field.rs, lenia.rs(×2), perturbation.rs |
| `.cos()` | perturbation.rs(`weight_at`) |
| `.exp()` | lenia.rs(`KernelCore::Exponential` / `GrowthMapping::Exponential`) |
| `.powi()` | lenia.rs(`KernelCore::Polynomial` / `GrowthMapping::Polynomial`) |
| `.floor()` | lenia.rs(カーネルのリング判定) |
| `.ceil()` | perturbation.rs(`accumulate_into` の到達半径) |

合計6箇所・5種類のメソッド。`libm` crate(no_std 対応の libm 実装、これも
esp-hal のエコシステムでよく使われる)の自由関数(`libm::sqrtf` 等)に置き換える
だけで済む。`powi` だけは libm に相当品が無いので、`x*x*x*x` のような手書きの
掛け算に展開する(元々指数は 4 固定なので難しくない)。

対応方針は、呼び出し側を直接 `libm::sqrtf(x)` に書き換えるのではなく、
`body` 内に小さな数学シム(`fn sqrtf(x: f32) -> f32` 等)を1つ置き、
`std`/`no_std` を cargo feature で切り替える形にする。呼び出し側のコードは
`x.sqrt()` から `sqrtf(x)` への書き換えで済み、PC版・M5Stack版で同じ
`body` クレートのソースを共有できる(予測可能性: 同じ処理は同じパターンで書く)。

## 埋め込みに伴う簡略化

- `assets/animals.json` の JSON + serde 読み込みと RLE デコーダ(`animal.rs`)は
  フラッシュ・RAM の節約のため M5Stack 版では使わない。4体切り替えは不要で、
  Orbium 1体分のパラメータとパターンを Rust の const 配列として埋め込む
  (CLI 引数での生物切り替えは PC版だけの機能に留める)
- 場のサイズは PC版と同じ 32x32 のまま(R=13 なら約440タップ、1ステップあたり
  約45万回の積和。ESP32 のクロックなら 15 step/s でも十分に余裕がある見込みだが、
  実機での実測は未検証)
- `render/dot_grid.rs` のピクセルフォーマット(premultiplied ARGB8888、`wl_shm` 用)
  は Wayland 固有なので流用しない。`embedded-graphics` crate 経由で RGB565 へ
  描く新しいレンダラを書く。プーリング(`pool_cell`)や色のブレンドの考え方
  (体の色とechoの色を混ぜる)はロジックとして流用できる
- `shell/layer.rs`(wlr-layer-shell)は無関係。M5Stack側の「shell」に相当するのは
  SPI 画面への書き込みとボタン/タッチのポーリングを回すメインループだけで、
  コンポジタに相当するものは存在しない

## 入力(IF層)の作り直しが必要な点

マウスのホバー/クリックという概念は物理ボタン・タッチパネルにそのまま
写像できない。

- **Core(物理ボタンA/B/C)**: ボタン押下を「決まった位置へのクリック」に
  割り当てるか、ボタンで走査位置を送り(十字キー的に)決定ボタンでクリックする
- **Core2/CoreS3(静電容量タッチ)**: 画面座標をそのまま `DotGrid::cell_at`
  相当の逆写像でセル座標に変換できる。PC版の `interface::pointer` に最も近い

いずれのモデルかで実装がかなり変わるため、**モデルが確定してから
`interface` 相当のモジュールを設計する**。

## 「環境ストレス」に相当する入力の再検討

PC版の `interface::machine_load`(CPU負荷→エネルギー減衰)は、M5Stack という
別の体にはそのまま持ち込めない。M5Stack 自身の CPU 負荷を読むことは技術的には
できるが、意味が無い(常時ほぼアイドルの組み込み用途であり、「機械が忙しい」が
起こりにくい)。この体で「環境ストレス」に何を割り当てるかは、この体を作る際に
改めて考える(未確定。候補: バッテリー残量、周囲温度・照度センサ〈搭載モデルのみ〉、
何も割り当てず気分状態はタッチ/ボタンの頻度だけで決める、など)。

### step 3: 実機で本当に生物が生き続けることを確認した

`m5stack-cores3/`(`vmc-pet-body` に依存する、独立した第二の Cargo プロジェクト。
デスクトップ版のワークスペースには含めていない — 理由は後述)を作り、
CoreS3 実機に実際に書き込んで検証した。

当初、生成テンプレートの `log` クレート経由(`log::info!` + `esp_println::logger`)
では、なぜか ANSI カラーコードと `INFO - ` の接頭辞しかシリアルに出力されず、
肝心のメッセージ本文が一切出てこないという問題にぶつかった(原因は特定できて
いない)。`esp_println::println!` に直接切り替えたところ問題なく出力されるように
なったため、ログは `log` クレートを介さずシンプルな `println!` 系だけを使う
方針にした。

また `no_std` + `alloc` のビルドには `.cargo/config.toml` の
`[unstable] build-std = ["core", "alloc"]` が要る(`esp-generate` の既定は
`["core"]` のみで、`alloc` を使うと `can't find crate for alloc` になる)。

実機でのシリアル出力(抜粋、66ms/step で駆動):

```
vmc-pet-cores3: loading Orbium unicaudatus
vmc-pet-cores3: loaded Orbium unicaudatus R=13 T=10
vmc-pet-cores3: initial mass=76.86
vmc-pet-cores3: step=   15 mass=73.92
...
vmc-pet-cores3: step=  585 mass=73.39
```

585 ステップ(約39秒)を通じて総量は 73.2〜74.0 の範囲で安定し、PC版で実測した
健常な Orbium の総量(73.7 前後)と一致する。**同じ Lenia のロジックが、実機の
上でも同じように生物を生かし続けられることを確認した。** JSON(`assets/animals.json`)
のパースも `serde_json` の `alloc` フィーチャで実機上に埋め込んだまま動いており、
懸念していた「フラッシュ・RAM節約のため生物を const 配列に固定する」簡略化は、
少なくともこの段階では不要だった(バイナリサイズは 140KB、16MB フラッシュの
0.86%)。

`m5stack-cores3/` はデスクトップ版の Cargo ワークスペースには含めていない。
含めると `cargo build --workspace` がこの crate も対象にしてしまい、
デスクトップ向けターゲットでは esp-hal 系の依存が解決できずビルドが壊れる。
`Cargo.toml` に空の `[workspace]` を置いて親のワークスペースから独立させてある。

### step 4: 画面にドットグリッドを描く

CoreS3 の画面(ILI9342C、AXP2101電源・AW9523B経由のリセットが要る)の初期化を
自前で書くのは大掛かりになるため、ボードサポートクレート
[`core-s3`](https://github.com/anapeksha/core-s3-rs)(MIT, v0.5.0)を使った。
`CoreS3::init_display(CoreS3DisplayResources { .. })` に SPI2/I2C0 のペリフェラル
とピン(GPIO3/11/12/35/36/37等)を渡すだけで、`embedded-graphics` の
`DrawTarget<Color = Rgb565>` を実装した画面が得られる。ピン配置やハードウェア
初期化の手順は、このクレートの `examples/hello_world` を読んで確認した。

`core-s3` が固定している依存バージョン(esp-hal 1.1.2, esp-alloc 0.10.0,
esp-backtrace 0.17.0, esp-println 0.15.0)に、こちらの Cargo.toml も合わせる
必要があった。合わせないと esp-backtrace のパニックハンドラが重複するなど、
依存関係の衝突でビルドが通らない。

`src/render/dot_grid.rs` と同じ考え方(値が大きいほど大きな円、面積が値に比例する
よう半径は sqrt をとる)で、`embedded_graphics::primitives::Circle` を使って
32x32 の場を描く関数を書いた。色は `Rgb565` に変換した固定色1色(PC版の
BODY_COLOR相当)で、echo(入力の可視化)に相当するものはまだ無い。

実機に書き込み、シリアル出力で確認した。800ステップ以上にわたってパニックなく
動き続け、総量も 73.3〜73.9 で健常なまま安定している。ユーザー自身が実機の
画面で、実際にドットが表示されていることを確認した。

#### ちらつきと不安定なフレームレートを、差分描画で改善した

ユーザーから「ちらつきがある」「フレームレートが安定しない」「画面解像度的に
左右に空きがある」というフィードバックを受けた。

まず左右の空きは、セルの縦横ピッチを画面の短辺(高さ)基準の正方形に揃えていた
ことが原因だった(320÷32=10px、240÷32=7.5px→7px、短い方に合わせるため横に
32×3px ぶんの余りが出る)。ドットの大きさ(半径)は重ならないよう短い方の
ピッチのままにし、ピッチそのもの(セル間の間隔)だけを画面の実寸(横320px・
縦240px)いっぱいに広げるよう修正した。

ちらつきと不安定さは、毎フレーム画面全体を `clear` してから描き直す素朴な
実装が原因だった。実測すると、15ステップぶんの間隔が2秒のときも4秒のときも
あり、一定していなかった(`STEP_INTERVAL=66ms` の狙いに対してかなり遅く、かつ
不安定)。描く必要のあるセル数がその時々で変動する(Orbium 自体が脈動しながら
動くため)ことが、ばらつきの原因と見た。

そこで `DotRenderer` に前フレームの各セルの半径を覚えさせ、**半径が変化した
セルだけ**、古い半径の円を背景色で消してから新しい半径の円を描くようにした。
変化していないセルには一切触れない。全画面 `clear` はしない。

同じ条件(15ステップぶんの間隔)で比較すると:

| | 修正前 | 修正後 |
|---|---|---|
| 間隔のばらつき | 2秒〜4秒 | 1.1秒〜2.3秒 |

理想値(0.99秒)にはまだ届いていないが、ばらつきの幅ははっきり縮まった。
ユーザーが実機で確認し、「ちらつきは感じないくらいに改善された」ことを確認した。

#### 左右の空きを、間隔ではなく実際のセル数を増やして埋める

前項の対応は、ドットの間隔(ピッチ)だけを画面幅いっぱいに広げるもので、
場そのもの(32x32)は変えていなかった。ユーザーから「セルの数を横方向だけ
変えるのは難しいか」という提案を受けた。

`Field`/`Lenia` は最初から幅・高さを独立したパラメータとして持っており
(`Field::new(width, height)`)、正方形を前提にしていない。カーネル(半径R)も
場の形とは無関係に円形に定義されるため、横長の場でも動くはずだと考えた。

PC側で実際に検証してから反映する、という他の変更と同じ手順を踏んだ。
32x32(基準)・42x32・43x32・45x32・32x42 の5パターンで Orbium を900ステップ
動かし、総量を比較した。

| 場のサイズ | t=0 | t=300 | t=600 | t=900 |
|---|---|---|---|---|
| 32 x 32 (基準) | 76.86 | 73.49 | 73.72 | 73.47 |
| 42 x 32 | 76.86 | 73.47 | 73.66 | 73.45 |
| 43 x 32 | 76.86 | 73.46 | 73.62 | 73.45 |
| 45 x 32 | 76.86 | 73.47 | 73.67 | 73.45 |
| 32 x 42 | 76.86 | 73.88 | 73.40 | 73.30 |

すべて基準(32x32)と同じ健常域に収まり、非正方形の場でも Lenia の挙動は
変わらないことを確認した。

これを踏まえ、`FIELD_WIDTH` を 32 から 43 に変更した(高さは 32 のまま)。
43 は `320 ÷ (240 ÷ 32) ≈ 42.67` の近似値で、これによりセルピッチが横 7.44px・
縦 7.5px とほぼ等しくなり、画面いっぱいに実際のセル(=本物の場のデータ)が
敷き詰められる。「間隔を広げて見た目を埋める」から「実際に描画する場のデータ
そのものを増やす」に変えたことで、境界の明確性(見えているドット数=場の
セル数)がより素直になった。

実機に書き込み、シリアル出力で健常な総量(73.2〜74.0)が保たれていることを
確認した。

### step 5: タッチを Touch へ変換する

PC版と同じ `Touch` / `body_perturbation_for` / `echo_perturbation_for` を
`vmc_pet_body` から共有する形にしてから実装した(前節「Touch/TouchEcho の
共有化」参照)。触れ方の意味づけは PC版と揃えてある。

- **タップの瞬間(`TouchPhase::Down`)** → `Touch::Click`。体への実注入と
  echo への強いフラッシュの両方が起きる
- **触れている間ずっと(`TouchPhase::Down`/`Move` の間)** → 毎ループ
  `Touch::Hover` を送り続ける。体には触れず、echo だけが光る
  (PC版の「ホバーは体に触れない」設計をそのまま踏襲している)
- **離した瞬間(`TouchPhase::Up`)** → 何もしない(PC版の `Touch::Leave` と同じ)

タッチコントローラは FT6336U(`core-s3::touch::Ft6336u`)。`parts.internal_i2c`
(ディスプレイ初期化と同じ内部 I2C バス)で構築し、40ms 間隔でポーリングする
(`core-s3` の `touch_demo` example に倣った値)。画面座標→場のセルの変換
(`DotRenderer::cell_at`)は、描画側の座標変換(セルピッチ・原点)と同じ場所に
持たせ、見えている位置と当たり判定がずれないようにしてある(PC版の
`DotGrid::draw`/`cell_at` と同じ考え方)。

`DotRenderer` も、体の値と echo の値のうち大きい方でドットの大きさを決め、
echo が占める割合で色を体の色(ティール)から echo の色(暖色の白)へ混ぜる
よう拡張した(PC版の `dot_grid.rs` と同じ合成方法)。半径だけでなく色も
前フレームと比較し、どちらかが変化したセルだけを描き直す。

実機に書き込み、シリアル出力で確認した。`touch controller init ok` が出て
FT6336U の初期化に成功していること、330ステップ以上パニックなく動き続け
総量・エネルギーが健常なまま推移することを確認した。**このサンドボックスには
実際に画面を指で触れる手段が無いため、タッチしたときに実際に体・画面が反応する
かどうかは検証できていない。** ユーザー自身が実機を指で触れて確認する必要がある。

#### タッチ実装がフレームレートを悪化させていたバグを直した

ユーザーから実機確認で「タッチには反応するが、全体的にフレームレートが低下して
タッチの判定が悪い」というフィードバックを受けた。

原因は明確なバグだった。`renderer.update()`(画面全体の差分描画、コストが高い)
を、体が実際に1ステップ進んだとき(`STEP_INTERVAL=66ms` ごと)だけ呼ぶのではなく、
タッチのポーリングループ(`TOUCH_POLL_INTERVAL=40ms` ごと)の中で無条件に
呼んでしまっていた。タッチの読み取り自体は軽い I2C 通信だが、描画は重い SPI
書き込みを伴う。結果として描画頻度が実質2倍近くに増え、フレームレート全体が
悪化していた。

「タッチのサンプリング(軽い、頻繁でよい)」と「画面の再描画(重い、体が進んだ
ときだけでよい)」を分離し、`renderer.update()` を再びステップ条件の内側に
戻した。タッチの読み取り・echo への反映(`apply_touch`)・echo の減衰は
これまで通り毎ポーリング行われるので、タッチの状態自体は変わらず即座に反映
される。反映が画面に見えるまでの間隔だけが、描画の実際のコスト(体のステップ
頻度)に揃った。

実機で実測すると、15ステップぶんの間隔がバグ混入前(1.1秒〜2.3秒)とほぼ同じ
1.84秒前後で安定するようになった(バグ混入時は2秒〜4秒だった)。

#### タッチしても無反応な場合が多い問題を、状態遷移の自己判定で軽減した

ユーザーから「タッチしても無反応のときが多い。反応するときもあるので
サンプリングレートの関係かも」というフィードバックを受けた。この仮説は
実装を見返すと的中していた。

以前の実装は、ハードウェアが返す `TouchPhase::Down`(押した瞬間を示す
フェーズ)を検知したときだけ `Touch::Click` を発火していた。ところが
`renderer.update()`(重い SPI 描画)の実行中はポーリングループが完全に
止まる。ちょうどその間に「押して離す」という速いタップが完結すると、
`Down` フェーズのサンプルを一度も読めないまま次のポーリングでは既に
`Move` か `Up`(あるいは何も無い)になっており、`Down` 頼りの判定では
そのタッチを丸ごと見逃していた。

ハードウェアの `Down` フェーズに頼るのをやめ、**「直前のポーリングでは
無反応(`None`)だったのに、今回は何か触れている」という自分自身の状態遷移**
で新規タッチを判定するよう変更した。これにより、描画で遅れて実際の `Down`
サンプルを取りこぼしても、指がまだ触れている限り(`Move` として観測されて
いても)次のポーリングで新規タッチとして検知できる。

なお、これは根本的な解決ではない。触れている時間そのものが、描画で
ポーリングが止まっている間隔(実測でおおむね80〜160ms)より短い、本当に
一瞬のタップは、指を置いている間サンプルする機会が一度も無いため、原理上
検知しようがない。この場合の対策は、描画のブロッキング時間そのものを
縮める(embedded-graphics の描画をより最適化する、SPI クロックを上げる等)
方向になる。

ユーザーが実機で確認し、「改善された」ことを確認した。

### フレームレート改善を試みた記録

ユーザーから「フレームレートを改善して」という依頼を受け、実機に計測用の
一時的なコードを仕込んで(`body.step()` と `renderer.update()` それぞれの所要
時間を `Instant` で測り、15ステップごとに平均をシリアル出力する)ボトルネックを
実測した。

| | 平均(15ステップごと) |
|---|---|
| `body.step()`(Lenia の畳み込み) | 約72ms |
| `renderer.update()`(SPI描画) | 約5〜7ms |

**描画は最初から支配的な要因ではなかった。** 1ステップの実測(66msの目標に対し
実際は約77〜122ms)のほとんどは、体そのもの(Lenia の畳み込み)の計算コストが
占めていた。これは 43x32 の場に対してカーネル半径 R=13(直径26)というカーネルが
相対的に大きく、活性セル(値が無視できないセル、実測 O2u で約215/1376)それぞれに
カーネルの全タップ(半径13の円で約450タップ)を畳み込むコストが、この CPU では
無視できない重さになっていたためと見ている。以前「描画のブロッキング時間が
80〜160ms」とタッチの節で書いたのは、実際にはこの `body.step()` の時間も含めた
値だった(両方とも同じ if ブロックの中で実行され、ポーリングをブロックする)。

以下、実際に試した4つの手と結果:

1. **`opt-level` を `'s'`(サイズ優先)から `3`(速度優先)へ変更 → 採用**
   `m5stack-cores3/Cargo.toml` の release プロファイルは esp-generate の
   テンプレート既定値のまま `opt-level = 's'` になっていた。フラッシュは16MBに
   対しバイナリは1%程度しか使っておらず、サイズを削る理由が無かった。
   `3` に変えたところ `body.step()` が約72ms→約62ms(約14%改善)。挙動は
   変えない安全な変更なので採用した。

2. **CPU クロックを既定の80MHzから240MHz(`CpuClock::max()`)へ → 実機がUSBから
   消え、撤回**
   esp-hal の `CpuClock` の既定値は80MHzで(`esp-hal` の
   `soc/esp32s3/clocks.rs` で `#[default] _80MHz` と定義されている)、公式の
   使用例にも `esp_hal::Config::default().with_cpu_clock(CpuClock::max())` が
   載っている。CPUバウンドなこの用途なら3倍のクロックが効くはずだと考え試した
   ところ、書き込み後に実機が `lsusb` からも消え、シリアル・espflash のどちらにも
   応答しなくなった。ユーザーに実機のリセットを依頼したところ復帰はしたが、
   代わりに画面に残像(後述)が出る状態になっていた。ソースは既定値(80MHz)へ
   戻し、書き込み直して正常動作を確認済み。**なぜ壊れるのかは未調査**。
   USB Serial/JTAG のクロックが CPU クロックと連動しているためではないかと
   推測しているが、確証は無い。

3. **描画を「消す円→描く円」の2回描画から、外接矩形1枚の `fill_contiguous` へ
   統合 → 実機で残像バグが出て撤回**
   同心円(消す円・描く円は常に同じ中心)なら、大きい方の外接矩形を1回
   `fill_contiguous` で塗り(内側は新色、外側は背景色)、erase→draw の2回描画を
   1回にできるはずだと考えて実装した。実機に書き込むと、**生き物が動いた後ろに
   薄い跡が残る**という描画バグが発生した。

   切り分けのため、まず「(2)のCPUクロック変更が原因では」と疑い、既定の
   80MHzに戻したビルドで再検証したが、残像は変わらず出た(このため
   (2)は無関係と判明)。次に「複数行にまたがる単一アドレスウィンドウの
   一括転送を、パネル/`core-s3`が想定通り扱えていないのでは」と疑い、
   1行ずつ個別に `fill_contiguous` を呼ぶよう書き直したが、これでも残像は
   消えなかった。最後に「消す円と描く円を完全に元の2回描画に戻す」ところ
   まで戻したところ、残像は消えた。

   これにより原因は SPI 側の転送方式ではなく、**自前で書いた距離判定による
   円のラスタライズが、embedded-graphics の `Circle` のラスタライズと
   ピクセル単位で厳密に一致していなかったこと**だと切り分けられた
   (数フレームに一度でも取りこぼしたピクセルがあれば、次のフレーム以降その
   セルの半径・色が変化しない限り再描画されないため、消し残しが蓄積して見える)。
   描画コストはそもそも1ステップの1割未満(上記の72ms対5〜7ms)で最適化の
   価値が薄いと判明していたため、正確なラスタライズを再実装するより、
   素直な2回描画に戻すことを選んだ。

**結果**: `opt-level=3` の変更(約14%改善)のみを採用し、他の2つは撤回した。
理想値(15ステップ≈0.99秒)にはまだ届いておらず、実測は約1.8〜1.9秒前後
(バグ混入前の1.84秒からほぼ変わらず)。`body.step()`+`renderer.update()`の
実測合計(約66ms)だけでは1ステップの間隔を説明しきれないが、これはメインループが
「タッチのポーリング間隔(40ms)」ごとに `delay` で必ず一度眠ってから次の判定に
入る作りのため(タッチ応答性を優先し、ステップの判定頻度をポーリング頻度に
揃えている)、体の計算時間(約66ms)に対してポーリング周期(40ms)の端数分の
待ちが毎回上乗せされるためと見ている。これは意図した設計(タッチのサンプリングを
軽く・頻繁に保つ)の副作用であり、バグではない。
ボトルネックが体の計算そのものだと判明したことで、次に取り組むべき方向が
(描画の最適化ではなく)Lenia の畳み込みアルゴリズム自体の高速化だと明確になった。

### Lenia の畳み込み(`crates/vmc-pet-body/src/lenia.rs`)を高速化した

`accumulate_potential`(体の畳み込み本体)は、活性セル(値が無視できないセル、
O2u で約215/1376)それぞれについて、カーネルの全タップ(半径13の円で約450)を
走査してポテンシャルへ加算するスキャッタ型になっている。各タップごとに
「トーラス境界を越えた分だけ折り返す」ための分岐が x・y それぞれで発生しており
(1ステップあたり約96,750回のタップ処理×2軸=約19万回の分岐)、これが
`body.step()` の時間の大部分を占めていた(前節参照)。

この分岐を、あらかじめ計算しておいた折り返しテーブルの参照に置き換えた
(`WrapTables`)。テーブルは `オフセット(-radius..size+radius-1) → 折り返し後の
座標(0..size)` を引けるようにしたもので、場の大きさが変わらない限り(通常は
起動時の1回だけ)使い回す。カーネルのタップは `|dx|,|dy| < radius` に絞り込まれて
いる(`build_kernel_taps` 参照)ため、テーブルの添字が範囲外になることはない。

**この変更は畳み込みの計算内容そのものは一切変えていない**(同じ剰余演算を
先に計算しておくだけで、浮動小数点の加算順序も完全に同じ)。そのため、変更前後で
出力が完全に一致することを検証してから反映した:

1. 変更前のコードで、O2u を43x32の場に置いて40ステップ動かし、5ステップごとの
   総量・チェックサム・特定セルの値をゴールデン値として記録する一時的な検証
   スクリプトを実行した。
2. 折り返しテーブルへの置き換えを実装した。
3. 同じスクリプトを再実行し、8つのチェックポイントすべてで小数点10桁まで
   完全に一致することを確認した。
4. `crates/vmc-pet-body` の既存テスト56件(質量保存・トーラス上での滑空・
   growth_scale の崖など)がすべて通ることも確認した。

実機(M5Stack CoreS3)に書き込み、シリアル出力で健常な質量・エネルギーの推移を
確認したうえで、15ステップぶんの間隔を計測した:

| | 15ステップの間隔 |
|---|---|
| `opt-level=3` のみ(前節時点) | 約1.8〜1.9秒 |
| 上記 + 折り返しテーブル | 約1.63秒 |

body.step() 自体の計算量は大きく減ったはずだが、外から見た間隔の改善幅
(約11〜13%)はそれより小さい。これはメインループが「タッチのポーリング間隔
(40ms)ごとに一度必ず眠ってから次を判定する」作りになっているため、体の計算が
速くなっても、判定のタイミングそのものが40ms刻みの階段状になっており、そこで
頭打ちになっているためと見ている(前節で触れた「ポーリング周期の端数分の待ち」
と同じ構造)。理想値(15ステップ≈0.99秒)に近づけるには、この判定周期の階段
自体を見直す必要がありそうだが、それはタッチの応答性とのトレードオフになる
別の検討事項であり、今回は畳み込み自体の高速化にとどめた。

### 体・入力の翻訳・崩壊検知・echo を PC版と共有する(`vmc_pet_body::Pet`)

ユーザーから「世界モデルとコントローラへの分割を進めて計算をPC側に寄せる
ことで改善できないか」という提案を受けた。フレームレート目的では、
(a) 当時の残りのボトルネックが計算ではなくタッチのポーリング周期由来の
頭打ちだったため効果が薄く、(b) 「PC版の表示器にはせず、M5Stack自身が
独立した体として動く」という既存の方針(docs/DESIGN.md「将来の拡張」)を
覆すことになるため、採らなかった。詳細な検討経緯は docs/DESIGN.md
「PC/M5Stack どちらでも世界モデルを動かせるようコードを整理する」参照。

ただしユーザーの関心は速度そのものではなく、World Models の
M(世界モデル)/C(コントローラ)の境界を実際のコード構造として引き直す
ことにあったため、その整理だけを行った。`crates/vmc-pet-body/src/pet.rs`
に `Pet` を新設し、PC版(`app.rs`)・M5Stack版(この `main.rs`)の両方が
それぞれ自前で持っていた以下のロジックを一本化した:

- 体(`LeniaBody`)への入力の翻訳(`Touch` → 摂動、`body_perturbation_for` /
  `echo_perturbation_for` の呼び出し)
- **崩壊検知と置き直し**。1ステップ進めるたびに総量を確認し、閾値を下回って
  いたら `revive()` する
- echo(入力の可視化)の保持・減衰

この整理で、以前は気づいていなかった重大なギャップが見つかった。
**M5Stack版にはこれまで崩壊検知が一切実装されていなかった**
(PC版の `app.rs` にはあった)。つまり、もし実機で体が崩壊していたら、
このM5Stackは二度と生き返らないままになっていたはずである。`Pet::step()`
自身がこの安全装置を持つようになったことで、この抜けは自動的に塞がれた。

「新しいタッチか」の判定(ハードウェアの `Down` フェーズに頼らず、状態遷移
から自前で検知する。前述「タッチしても無反応な場合が多い問題」参照)は、
`Pet` には持たせず、この `main.rs` 側に残してある。PC版はウィンドウ
システムの明示的な Press イベントで判定できるため、この判定方式は
入力デバイスに固有の事情であり、共有すべき部分ではないと判断した。

このリファクタリングによって、実機での挙動(質量・エネルギーの推移、
描画・タッチの見た目)が変わっていないことを、書き換え前後で同じ
シリアル出力(健常な質量・エネルギー)を確認して検証した。PC版・M5Stack版
どちらとの通信も一切作っていない。あくまで「同じロジックを2つの
プラットフォームで動かせる形に整理した」だけである。

### 自律コントローラ(体の形に反応して自分から働きかける)を実装した

M/Cの境界を引いた後、`AutonomousController`(体の形の歪みを観測し、周期的に
自分自身を軽くならす)を実装し、`Pet::step()` に組み込んだ
(docs/DESIGN.md「自律コントローラ(C)を実装する」参照)。`Pet::step()` を
呼ぶだけの M5Stack版は、コード変更なしにこの新しい振る舞いを自動的に
獲得している。

実機に書き込み、シリアル出力で健常な質量・エネルギーの推移(タッチせずに
放置してもエネルギーが従来通り減衰していく)を確認した。自己摂動は
`LeniaBody::disturb` を通るためエネルギーには影響せず、コントローラが
体の世話の代わりになってしまう(放置してもエネルギーが尽きなくなる)ことは
ない。**画面上で見て分かるほどの動きになっているかは、実機の画面を見た
ユーザー自身の確認が要る**(2秒に1度、条件を満たしたときだけの控えめな
自己摂動のため、気づきにくい可能性がある)。

### カメラ追従(表示原点を重心へ寄せる)をPC版と共有した

ユーザーの依頼で、PC版(`app.rs` の `Camera`)と同じく、表示原点を生物の
重心へ寄せる対応をM5Stack版にも入れた。`Camera`(トーラス上の重心計算を
含む)は元々 `src/render/camera.rs` にあった PC専用実装だったが、
`.rem_euclid()` が `std` 専用(実測済み)だったのを `crate::math::rem_euclidf`
のシムに置き換えたうえで `crates/vmc-pet-body/src/camera.rs` へ移し、
PC版・M5Stack版のどちらも同じものを使うようにした。

M5Stack版はPC版と違い、場(43x32)と画面上のドット数が最初から 1:1 対応して
おり、PC版のような「高解像度の場を低解像度の表示にプーリングして落とす」
処理が無い。そのため `DotRenderer` では、画面のスロット (column, row) に対して
`カメラ原点の整数部だけずらした場のセル` を表示し(プーリングの代わり)、
`カメラ原点の小数部` はドットを描く画面座標だけをサブピクセル単位でずらす
(PC版の `DotGrid::draw` と同じ考え方)。前フレームとの差分描画
(`previous_radius`/`previous_color`)は画面上のスロット位置を指すので、
カメラが動いて場のセルとの対応がずれても壊れない。

タッチ位置から場のセルへの変換(`cell_at`)も同じ変換を経由するよう直した。
これを忘れると、画面に見えている位置と実際に反応する位置がカメラの移動分
だけずれてしまう。

実機に書き込み、シリアル出力で健常な質量・エネルギーの推移(体そのものの
挙動はカメラ・描画の変更で変わらないはず)を確認した。**表示が実際に
重心へ追従して見えるか、タッチ位置と反応がずれていないかは、実機の画面を
見たユーザー自身の確認が要る。**

## 未確定・要相談事項
